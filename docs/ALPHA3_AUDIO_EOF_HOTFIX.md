# alpha.3 QQ 曲末尾音修复

## 范围与证据

- 工作目录固定为 `F:\Codex\CloudXMusic\v2.5.0-alpha.3`，版本仍为 `2.5.0-alpha.3`。
- `QQAudioPlayer.decode()` 原来在解码结束后调用 `quiet()`；该方法最多等 180ms 后执行 `stop/flush/close`，自然结束没有调用 `drain()`。驱动尚未消费的 PCM 可能被清掉。这是已确认的截尾风险，不足以单独证明实机提前数秒的全部原因。
- FLAC 会跳过元数据块，并验证 STREAMINFO 样本数和 PCM MD5；样本缺失会报错。MP3 通过现有 JLayer 逐帧解码，直到没有可解码帧。没有新增解码库。
- QQ 客户端不根据接口 `duration` 定时切歌。`QQPlaybackController` 只在音频状态为 FINISHED 后推进个人队列；房间模式只向 `MusicRoomClient.qqAudioFinished()` 发送完成通知。

## 调用链与线程边界

| 入口/链路 | 上下文与所有者 | 处理与生命周期 |
| --- | --- | --- |
| 解码 EOF → `finishOutput()` | QQ 解码虚拟线程 / 当前 Session | 独立自然结束路径，等待 `SourceDataLine.drain()`；等待时不持有输出锁。 |
| `pause()` / `resume()` | QQ 音频控制线程 / Session 输出锁 | 排空期间暂停只停止输出线，保留排队 PCM；恢复使用同一条输出线继续排空。其他暂停路径维持原行为。 |
| `stop()` / 换曲 / 关闭 | QQ 音频控制线程 / Session 输出锁 | 标记取消并 stop/flush/close，解除 drain；取消的会话不得发布 FINISHED 或回调下一曲。 |
| 排空 → FINISHED → 控制器 | 解码后台完成 → 既有客户端回调分发 | 输入正常关闭之后再公开 FINISHED；轮询和显式回调共用原有播放代次去重。 |
| 房主完成 → 原协议控制包 | Minecraft 客户端线程 / 房间状态 | 沿用原房主权限、MID、时间轴代次、循环模式与去重保护；听众不能本地推进。 |

排空等待不会占用游戏线程或音频控制线程；网络读取超时监测不用于截断排空。音频输出资源在自然完成、出错、停止、换曲及关闭路径释放，没有新增执行器或缓存。所有房间回调沿用现有客户端线程分发。本项目是 Fabric 客户端，不存在可应用 Paper/Folia 区域调度的本次变更。

## 日志与联机边界

- `[QQ音频EOF] PCM 解码结束，等待声卡排空`：记录已提交帧数、采样率、待播帧数和 PCM 时长。
- `[QQ音频EOF] 声卡已排空，发布播放完成`：该事件之后才允许自然完成回调。
- `[房间时间轴] 收到换曲/重播时本机尚未自然 EOF`：记录前后 MID、旧曲本机进度/时长、目标位置和广播代次。手动切歌也会出现该日志，必须结合实机操作判断。

服务端源码不在本工作区内。现有文档描述了服务端按时长自动推进队列；本次无法验证或修改该逻辑。为了保持服务端权威与协议兼容，客户端不延迟或丢弃有效的换曲广播，也不伪造歌曲时长来绕过服务端。若无手动切歌时仍出现第三条日志且没有先出现第二条日志，应继续检查服务端的自动推进条件与取链启动延迟。
